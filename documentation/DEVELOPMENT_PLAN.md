# Morph 2.0: план разработки по фазам

> **Статус: рабочий план поставки.** Спецификация того, *что* строим —
> в [`batch-orchestrator.md`](./batch-orchestrator.md) (EN) и
> [`NEW_PARADIGN.md`](./NEW_PARADIGN.md) (RU-нарратив). Этот документ
> фиксирует *порядок* и *критерии приёмки*.

## Регламент работы

- **Роли.** Delivery engineer (Claude, интерактивная сессия) ведёт диалог,
  нарезает фазы на джобы-спецификации, ревьюит результат и коммитит.
  **Код пишет исполнитель — агент claude-opus-5**, получая на вход
  спецификацию джоба. Push в `MorphReborn` выполняет владелец руками.
- **Дogfooding.** Спецификация каждого джоба оформляется в формате morph
  card (intent, target, context_slice, acceptance) — мы разрабатываем
  батч-оркестратор его же методом, ещё до того как он написан.
- **Правила приёмки.** Фаза закрыта, только когда её acceptance-критерии
  проходят механически (тесты/запуск), а не «на глаз». Каждая фаза —
  отдельный коммит (или серия), пригодный к пуш-окну.
- **Инварианты на всём протяжении.** Существующее интерактивное поведение
  (`/generate`, `/patch`, scheduler) не ломается ни в одной фазе;
  `tests/test_scheduler.py` остаётся зелёным всегда. Никаких новых тяжёлых
  зависимостей без согласования.

## Фаза 0 — Morph card: схема и валидатор

**Цель:** формат карты зафиксирован кодом раньше, чем появится любой
потребитель формата.

**Поставка:**
- `cards/schema.py` — датакласс/схема morph card: `custom_id`, `meta`
  (`intent`, `target`, `context_slice`, `acceptance`, `model`, `variants`,
  `generation`, `depends_on`), `instruction`; значения по умолчанию и
  валидация (интент из {generate, patch, todo}, variants >= 1 и т.д.).
- `cards/deck.py` — загрузка колоды из файла бэклога (JSON-список карт),
  проверка уникальности `custom_id`, разрешение `depends_on`.
- `tests/test_cards.py`.

**Приёмка:** `pytest tests/test_cards.py` проходит; битые карты (неизвестный
intent, дубль custom_id, циклическая зависимость) отклоняются с внятной
ошибкой.

## Фаза 1 — Deck-компилятор: карта → батч-запрос

**Цель:** из валидной колоды получается провайдер-специфичный JSONL.

**Поставка:**
- Режим списка файлов в `ContextFolderDialog` (context_slice) рядом с
  существующим walk-everything; пустой slice => whole-project (поведение
  Morph 1.0).
- `cards/compiler.py` — карта + срез контекста → self-contained запрос
  (наш `LLMDialog`-формат), затем сериализаторы: Anthropic Message Batches
  JSONL и OpenAI Batch JSONL. `variants: N` => N запросов с суффиксами
  custom_id.
- Golden-файлы ожидаемого JSONL в `tests/golden/`.
- `tests/test_compiler.py` (сравнение с golden).

**Приёмка:** компиляция эталонной колоды из 3 карт (generate + patch +
variants=3) байт-в-байт совпадает с golden-файлами обоих провайдеров.

## Фаза 2 — Батч-бэкенды в registry

**Цель:** submit / poll / collect как новый интерфейс процессора.

**Поставка:**
- Расширение `processors/registry.py`: у процессора появляется опциональный
  батч-интерфейс (`submit_deck`, `poll`, `collect`) рядом с синхронным `run`.
- Реализации для openai (Batch API) и anthropic (Message Batches; попутно —
  первый anthropic-процессор в registry).
- **Локальная эмуляция батча** для `llama_cpp`/`ollama`: колода дренится
  через существующий пул `JobScheduler` (K80-ноды как «ночной
  миникомпьютер»).
- `tests/test_batch_backends.py` на мок-API (без сети).

**Приёмка:** мок-тесты проходят; smoke-тест локальной эмуляции гоняет колоду
из 2 карт через фейковый processor и собирает оба результата.

## Фаза 3 — Поколения и зависимости

**Цель:** колода исполняется поколениями, зависимости не попадают в один
батч.

**Поставка:**
- `cards/generations.py` — топологическая сортировка колоды по `depends_on`,
  разбиение на поколения; карта с неудовлетворённой зависимостью ждёт
  следующего поколения.
- Цикл: скомпилировать поколение N → submit → collect → записать морфы
  (существующие `response_to_file_body` / нейминг `<name>.<custom_id>.<ext>`
  для вариантов) → поколение N+1.
- `tests/test_generations.py` (цепочка A→B→C деградирует в 3 поколения;
  широкая независимая колода — в 1).

**Приёмка:** тестовые сценарии проходят; лог исполнения показывает состав
каждого поколения до сабмита.

## Фаза 4 — Верификация и best-of-N

**Цель:** acceptance-критерий карты проверяется механически, лучший вариант
выбирается автоматически.

**Поставка:**
- `cards/acceptance.py` — раннер критерия (shell-команда из поля
  `acceptance`, таймаут, exit code => pass/fail), песочница: запуск в
  рабочей копии, откат непринятых морфов.
- Выбор варианта: первый прошедший acceptance; ни один не прошёл => карта
  падает.
- Пересборка упавших карт в поколение N+1: контекст ошибки (stdout/stderr
  раннера) добавляется в instruction; лимит перегенераций (по умолчанию 2).
- `tests/test_acceptance.py`.

**Приёмка:** сценарий «3 варианта, проходит только второй» выбирает второй;
сценарий «все упали» уводит карту в следующее поколение с приложенным
выводом ошибки и останавливается на лимите.

## Фаза 5 — CLI-оркестратор: пользовательский цикл

**Цель:** ночной морфинг доступен из `mrph` как связный workflow.

**Поставка:**
- Новые команды в `flows/morph.py`: `/deck` (показать бэклог и статус карт),
  `/card` (добавить карту диалогом), `/submit` (скомпилировать и отправить
  текущее поколение), `/collect` (забрать, верифицировать, интегрировать),
  `/nightly` (submit+poll+collect одним циклом).
- `/card` работает в двух режимах: ручное добавление одной карты и режим
  декомпозиции — «вот цель, предложи колоду»: оркестратор разворачивает
  намерение в набор карт с target/slice/acceptance, пользователь ревьюит.
  Холодный старт (пустая колода, включая генезис-паттерн для нового
  проекта) — см. «Where cards come from» в `batch-orchestrator.md`.
- Файл бэклога `.morph/deck.json` в корне проекта; состояние исполнения в
  `.morph/state.json` (переживает перезапуск CLI).
- Обновление `/help`, README и graphviz-графа бота.

**Приёмка:** сквозной прогон на этом самом репозитории: колода из 2
независимых карт проходит `/submit` → `/collect` на локальной эмуляции;
`/deck` корректно показывает статусы до/после.

## Фаза 6 (рисёрч) — лёгкая репрезентация проекта для оркестратора

**Цель:** оркестратор режет `context_slice` не вслепую. Открытый
исследовательский вопрос из манифеста — фиксируется отдельной спецификацией
после Фазы 5.

**Кандидаты:** карта репозитория (пути + сигнатуры), граф импортов,
эвристика «target + его тесты + его импорты». Критерий качества: доля карт,
прошедших acceptance с первого поколения, против whole-project baseline.

## Порядок и зависимости фаз

```
Ф0 (schema) ─→ Ф1 (compiler) ─→ Ф2 (backends) ─→ Ф3 (generations) ─→ Ф4 (acceptance) ─→ Ф5 (CLI)
                                                                                          │
                                                                Ф6 (research) ←──────────┘
```

Фазы 0–1 не требуют сети и провайдеров вовсе; Фаза 2 тестируется на моках;
реальный батч-провайдер впервые нужен только для smoke-теста Фазы 5.
